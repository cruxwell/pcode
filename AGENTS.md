# Development notes

## Workflow

- Always commit after changes. The global `pcode` is an editable install pointing at the mainline `src/`, so a merged change is live on the next start with no reinstall. Only `pyproject.toml`/`uv.lock` changes need `make install`, and the `.githooks/post-merge` hook runs it on the mainline when a merge touches them (needs `git config core.hooksPath .githooks`). That hook only fires on a merge: a dependency bump edited directly in the mainline checkout leaves the global `pcode` running new source against the old environment, and it fails at startup with an `ImportError` until you run `make install` there. Bump dependencies in a worktree, or run `make install` the moment `uv.lock` and the code that needs it change.
- `GIT_AUTHOR_EMAIL`/`GIT_COMMITTER_EMAIL` exported by a parent `.envrc` beat `user.email`, so a session started under a work root commits under a work address into this public history. `.githooks/pre-commit` and `pre-push` refuse that, but only once the clone has `git config --local user.email` set; `make sync` sets it and the hooks path. After any rewrite of origin's history, other clones must run `make sync` (or `git fetch origin && git show origin/master:scripts/sync.sh | sh`) before anything else: a plain `git pull` merges the old commits back and `post-merge` pushes them. Never run `make install` from a worktree: it repoints the global `pcode` at that branch.
- After finishing any non-trivial change, delegate a review of it to a sub-agent (it doesn't see this conversation, so pass the diff or commit range and the intent) and address its findings before calling the work done.
- Before touching terminal or agent integrations, read [dev/dependencies.md](dev/dependencies.md).
- `docs/` is the published user site (listed in `zensical.toml`): what a feature does and why you'd want it, not how it's built. Design notes, plans, runbooks and implementation detail go in `dev/`, which is not published, or in a code comment. A published page linking into `dev/` must use a full GitHub URL, since `dev/` is outside the site. `make docs` fails on a broken page or anchor link under `docs/` but never checks `dev/` or the README.
- `make harness-src` checks out the Pydantic AI repo (which holds Harness: source in `src/pydantic_ai_harness/pydantic_ai_harness/`, plus `docs/harness/` and `tests/harness/`) at the locked release under `tmp/pydantic-ai`. Read that rather than the website, which can describe an unreleased Coder API and extras. The old `pydantic/pydantic-ai-harness` repo is frozen; don't read it for current behavior.

## Testing and debugging

- `make test` skips the real-tmux regressions (75% of the runtime). Run `make test-all` before commiting anything touching layout, streaming, the editor, or the prompt. The tmux tests run in parallel and beside other worktrees' runs only because none of them races the clock, so a tmux test that fails under load has a timing dependency to fix, not a busy machine to wait out. The two traps: a scripted turn held open with a fixed `sleep` for the test to act inside (use `await gate()` and `release()`), and asserting on a transcript note shortly after a resize, split, or kill-pane. The debounced resize replay erases notes already on screen, so resize through `resize(pane, ...)` first. Compare against the same tests at `HEAD~1` (add a throwaway worktree and run it with `PYTHONPATH=<that>/src`, which wins over the editable install) before believing a regression.
- `make test-socket` (part of `make test-all`) reruns the fast suite with every `PreviewApp` session moved into a `SessionHost` over a real socket (`tests/socket_transport.py`). There the host's state (queue, prompt row, busy, side questions) reaches the terminal a moment after the runtime acts, so a test that sets an event inside a fake runtime and then asserts on `app.activity` must wait for the value instead. Keep your own handle on a fake runtime: `app.runtime` is the host's journal reader under that transport. Mark a test `@pytest.mark.in_process(reason)` only where hosted behavior is meant to differ (a hosted `/quit` detaches instead of cancelling).
- `tests/test_terminal.py` spawns real pcode with the real environment, so once a session worktree holds unmerged commits its Ctrl+D exit stops on "Merge and remove the worktree?" and the test times out. Uncommitted edits to tracked files skip the question, so it passes mid-change and starts failing the moment everything is committed. That failure is the worktree's state, not the change; confirm with the same test at `HEAD~1` in a throwaway worktree.
- Comparing a failure against `HEAD` in a throwaway worktree only works if the new path is the same length: console output is wrapped to a fixed width, so a shorter checkout path silently rewraps it and width-sensitive assertions (`test_mcp_enable`, anything matching a traceback line) flip. Name the worktree to match, or the comparison lies in both directions.
- When a test needs artificial CPU load, give each burner its own deadline (`python3 -c "import time; t=time.time()+60; exec('while time.time()<t: pass')" &`), never a trailing `pkill` in the same command. A stopped job, a closed session, or a `pkill` that fails under that very load ("Cannot get process list") leaves `while True` loops spinning at 100% per core until reboot; that happened here once with 16 of them.
- Never `git stash` here. Dozens of worktrees share one stash ref, so a concurrent session's push or pop can hijack yours: the entry you get back is somebody else's, based on a different commit, and it lands as conflicts. Commit to a scratch branch instead.
- Do not run another syncing `uv run` beside pytest in the same environment: it can briefly uninstall Harness while tests read its package metadata, causing misleading `PackageNotFoundError` failures. Use `uv run --no-sync` for concurrent read-only checks, or run them serially.
- `make test` is xdist-parallel and needs a stable tree: saving a file mid-run yields bulk failures or `Different tests were collected between gw0 and gwN`. Re-run on a quiet tree (or `uv run pytest -n0`) before believing a mass failure.
- `-n auto` is capped at 4 workers (`tests/conftest.py`) because several sessions running the suite at once exhausted RAM and swap. Don't pass `-n <cores>` to get around the cap; a full run on an otherwise idle machine can use `PYTEST_XDIST_AUTO_NUM_WORKERS=<n>`.
- `make install` is editable, so a running session keeps whatever source was on disk when each module was first imported: a mid-turn fix does not reach it, and a broken intermediate state stays loaded until restart. Before hunting an unreproducible failure, compare its timestamp against file mtimes and check whether another session was editing.
- This checkout's committed `.pcode/preferences.json` turns `worktree` on, so any test that launches pcode from the repo (a subprocess, or in-process `main()`) checks out a real `.worktrees/pcode-*` and waits on its `uv sync`: slow startups, timeouts, and leaked worktrees. `conftest.py` hides the overlay for in-process runs; subprocesses need `--no-worktree`, as the tmux `pane` fixture and `test_terminal.py` pass.
- Failed turns save their frames to `<session-dir>/errors.log`; the transcript's `turn_failed` record carries only a type and message.
- A capability's `wrap_model_request` cannot catch a provider error from a *streamed* request, which is every turn here. `ContinuationModel` defers the HTTP call to the first iteration of the event stream, so the wrap task is parked on `stream_done` and the exception surfaces in the consumer instead; `_agent_graph` also skips `on_model_request_error` whenever `stream_error` is set. Recovery that reacts to a failed provider response belongs in `AgentRuntime.stream`, which owns turn retries.
